## 2. 规划（Claude）

### 现状（量过）

- 35 个测试文件里写死的等待共 942 秒：不到 400ms 的 255 个（65 秒），400–999ms 的 421 个（231 秒），1–2.5 秒的 103 个（158 秒），**2.5 秒以上的 70 个（272 秒，其中 `s_sync` 92 秒、`s_read` 48 秒）**。
- 最费等待的文件（等待秒数）：`s_sync` 108、`s_read` 64、`s_bookpaged` 52、`s_dir` 51、`s_shell` 50、`s_text` 35、`s_reco` 34、`s_rich` 33。
- 大多数等待是“点了一下 / 发了个同步，等页面和假服务把事做完”，不是在等某个固定时间。

### 做什么

1. **`devtools/e2e/settle.js`**（新）：`settle(最多等多久)`——页面（含阅读页的 iframe）里没有 DOM 变化、没有请求在路上，并且已经安静了一小段时间，就马上返回；等到最多时间还没安静就返回（最坏和原来的写死等待一样久）。安静的时长按原来要等的时间定：约 20%，最少 0.3 秒、最多 0.8 秒；返回之前至少等这么久，这样页面里“过几百毫秒才发生”的事（防抖、定时器）不会被抢在前面看。
2. **把 400ms 及以上的 `await sleep(N)` 换成 `await settle(N)`**（不到 400ms 的不动：多半是在等防抖或动画的几帧），先改 `s_sync`、`s_read`、`s_bookpaged`、`s_dir`、`s_shell`、`s_text`、`s_reco`、`s_rich`。
3. **量**：改之前用 `run_all.ps1 -Only …` 记下这几个的耗时；改之后每个测试连跑三次，三次都要和改之前一样的结果（通过数不变），再记耗时；哪个测试出现时好时坏，就把那里的 `settle` 退回写死的等待（或者换成明确的条件）。
4. README 里写 `settle` 的用法和“最坏情况和以前一样”。
